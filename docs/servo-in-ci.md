# servo in CI

**Who this is for:** anyone adding servo to a CI pipeline, a merge queue or a pre-commit hook —
what to run, what it exits with, what it costs, and the repository settings that keep generated
files honest.

The rule fits in one line: CI runs `servo check`, never `servo generate`. `check` generates every
injector in memory, compares the result with the committed files, and compiles them; a file that
is stale, missing or broken fails the build instead of being quietly regenerated on a runner and
never committed.

## A workflow to copy

```yaml
# .github/workflows/servo.yml
name: servo

on:
  pull_request:
  push:
    branches: [main]
  merge_group: # check what a merge queue is about to land; see "Merge queues"

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    env:
      GOWORK: "off" # check what a checkout without your go.work generates; see "go.work and --scope"
    steps:
      # Pin both actions by commit SHA if your policy asks for it.
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-go@v7
        with:
          go-version-file: go.mod
      - run: go tool servo check
      # One more line per build variant the module generates:
      # - run: go tool servo check --tags=prod
```

`go tool servo` runs the generator version your `go.mod` pins — the one `go generate` ran on the
developer's machine — so CI and the commit can only disagree about the code, never about the tool.
That is what the tool directive is for; add it once per module with
`go get -tool github.com/okian/servo/v3/cmd/servo`. A `servo` installed with `go install …@latest`,
or baked into a CI image, becomes a different version the day servo releases, and a version
difference reads exactly like a forgotten regenerate.

`go tool` runs the tool the current module pins, so a repository with several Go modules runs one
`go tool servo check` per module, from that module's directory (`working-directory:` in Actions).

servo's own [`.github/workflows/go.yml`](https://github.com/okian/servo/blob/master/.github/workflows/go.yml)
runs `go run ./cmd/servo check --dir examples/…` instead. That works only inside servo's
repository, where `./cmd/servo` belongs to the module under test. In yours it is `go tool servo`.

## Exit codes

Every `servo` command exits **0 or 1**, so a CI step needs no special cases. `go tool` passes the
status through unchanged.

| Command | 0 | 1 |
| --- | --- | --- |
| `servo check` | every generated file is current and compiles | a file is stale, missing, left over or does not compile, or the graph has a diagnostic |
| `servo generate` | every file was written or already current | a diagnostic, or a written file that does not compile |
| `servo doctor` | no `[FAIL]` line (`[WARN]` and `[INFO]` never fail) | at least one `[FAIL]` |
| every other command | success, including `-h` | any failure, including a bad flag or an unknown command |

[`servo-vet`](reference/cli.md#servo-vet) is a separate binary built on `go/analysis`, and follows
its conventions instead:

| `servo-vet` run | Exit status |
| --- | --- |
| standalone, `go tool servo-vet ./...`: clean | 0 |
| standalone: findings | 3 |
| standalone: the analysis could not run (a package failed to load) | 1 |
| standalone with `-tags`, which it refuses | 2 |
| through the go command, `go vet -vettool=$(which servo-vet) ./...`: findings or failure | 1 |

## Upgrading servo

The version is the `github.com/okian/servo/v3` requirement in `go.mod`; the tool directive builds
exactly that. Upgrade the way you upgrade any dependency, then regenerate in the same commit:

```
go get -tool github.com/okian/servo/v3/cmd/servo@latest
go generate ./...
```

Generated code's internal shape is not covered by servo's compatibility promise, so a new release
can change committed files without any change of yours — which is why the regenerate belongs in
the upgrade's commit. Every generated file also names the runtime it needs, in a
`const _ = servoimpl.Contract1` line: a file generated by a newer servo than `go.mod` requires
fails to compile on that line, and the comment above it says to regenerate with
`go tool servo generate`.

## go.work and `--scope`

A `go.work` changes how the go command reads your code in two ways: it makes every module it
lists a main module, and it resolves those modules from their directories instead of the versions
your `go.mod` files require. servo ignores the first by default: under `--scope=module`, the
default, "the main module" is the module `--dir` is in and nothing else — the same module a
`GOWORK=off` build calls main. The second still applies, because servo loads code through the go
command: in a workspace, a sibling module's types and constructors come from your working copy.

So generate and check under the same conditions.

- If your `go.work` is not committed — the go command's own advice — CI runs without one, and
  `GOWORK=off`, as in the workflow above, says so explicitly (it is harmless where there is none).
  Run `GOWORK=off go generate ./...` locally before committing when you keep a workspace.
- `--scope=workspace` restores the pre-v3.5.0 reading, every listed module main: interface search
  reaches a sibling's implementations, and a sibling's `//servo:config` types are the graph's. Use
  it only if the `go.work` is committed and CI checks with the same flag.

`servo doctor` warns when a `go.work` lists more than one module, and the commands servo suggests
in its reports repeat the `--scope` they were run with.
[`--dir` and injector scope](reference/cli.md#--dir-and-injector-scope) is the reference.

## Build variants

A module that generates [build variants](reference/cli.md#build-variants) has one generated file
per configuration, and `check` inspects only the one its flags select, so CI runs one check per
variant:

```
go tool servo check
go tool servo check --tags=prod
```

`servo doctor` names the variants a run did not check, with the command that would.

## Cross-compiling `generate`

`GOOS` and `GOARCH` decide which files a load sees, so they reach servo through the environment, as
they reach `go build`. Under `go tool`, though, the go command reads them too and builds the tool
for that platform, which this machine cannot run:

```
$ GOOS=linux go tool servo generate
go tool servo: fork/exec …/servo: exec format error
```

Build the tool for this machine and hand the target to servo alone:

```
GOOS=linux "$(go tool -n servo)" generate
```

`go tool -n servo` prints the path of the binary `go tool servo` would run, without running it.
`GOOS` is not a variant axis: the file is written under the same name and constraint whatever
platform it was resolved for, so this only matters when your providers differ by platform. See
[Limitations](limitations.md#build-variants-only-cover-build-tags-not-goosgoarch).

## Vendoring

`go mod vendor` vendors the tool along with everything else — `cmd/servo` and its dependencies —
so `go tool servo check` works in a vendored module with no network, under the go command's default
`-mod=vendor`. The generated bytes do not depend on whether a module is vendored: committed files
carry no source positions, and servo's introspection commands print a position in another module by
its import path, vendored or not.

## Offline

With a warm module cache servo needs no network: `GOPROXY=off go tool servo check` works, and an
empty build cache only costs time, while the go command compiles servo and its dependencies before
running it.

## What it costs

`check` loads and type-checks your main module, reads the standard library from the compiler's
export data, resolves every injector and compiles the generated files. Measured with v3.4.1 on
darwin/arm64, wall time and peak memory, the ranges spanning several runs:

| Module | Warm caches | Empty build cache | Empty build and module caches |
| --- | --- | --- | --- |
| A small consumer: three packages, one injector | 0.3 s, 40 MB | 4.6 s, 300 MB | 5–10 s, 300 MB |
| servo's tutorial: 26 packages, four injectors, 158 modules | 0.8–2.1 s, 0.8 GB | 11–20 s, 1.1–1.3 GB | network-bound |

Two v3.5.0 changes move these: `check` now also compiles the files it finds current, about a second
more on the tutorial, and a run from an injector's directory costs what a run from the module root
does, since `--dir` no longer narrows the load. The empty-cache columns are the case a CI cache
avoids: `actions/setup-go` caches the module and build caches by default.

## Merge queues

Two pull requests can each pass `servo check`, merge without a conflict, build, pass their tests,
and still leave a stale file on the main branch. Say one branch gives a type a `Stop` method while
the other makes that type part of the graph for the first time. Neither branch's generated file
calls the `Stop` — the first because the type was not in its graph, the second because the type had
no `Stop` in its code — so git merges the two files cleanly, and the result never stops the
component. The generated file is a function of the whole graph, and a textual merge of two
generations is not the generation of the merge.

Only a check of the merged code notices. With GitHub's merge queue, add the `merge_group` trigger
the workflow above has, and make the check required: the queue then runs it on the exact commit it
is about to land. Without a queue, require branches to be up to date before merging, or at least run
the check on every push to the main branch so the drift is caught at once rather than by the next
unrelated pull request.

## `.gitattributes` and CODEOWNERS

```
# .gitattributes
servo*_gen*.go text eol=lf linguist-generated
```

The pattern matches every file servo writes, at any depth: `servo_gen.go`, the test variant
`servo_gen_test.go`, a build variant such as `servo.prod_gen.go`, and the config loaders,
`servo_config_gen.go`. `eol=lf` keeps a Windows checkout's copies byte-identical to everyone else's
(Git for Windows checks text out with CRLF by default; `servo check` normalizes line endings, other
tools may not). `linguist-generated` makes GitHub collapse those files in pull-request diffs and
leave them out of the language statistics; drop it if your reviewers read wiring changes there,
which is what the generated file is written for.

In CODEOWNERS the last matching line wins, so put the generated files' line last, either with the
team that reviews wiring or with no owner at all:

```
# .github/CODEOWNERS
# Generated by servo and verified by `servo check`, so a constructor change does not
# need sign-off from every team that owns a directory holding an injector.
servo*_gen*.go
```

## The pre-commit hook

[`githooks/pre-commit`](https://github.com/okian/servo/blob/master/githooks/pre-commit) is a
reference hook to copy into your repository. It runs `go tool servo check` against what is about to
be committed, not the working tree: unstaged and untracked changes are set aside with
`git stash push --keep-index --include-untracked` for the duration of the check and restored when it
ends, so a partial `git add -p` commit is checked as committed. Enable it per clone, from the
repository root:

```
git config core.hooksPath githooks
```

A module with build variants adds one `go tool servo check --tags=…` line per variant, as CI does.
The hook is a convenience, not the gate — anyone can commit with `--no-verify` — so keep the CI
check.
